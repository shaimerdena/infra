## 1. DevOps и SDLC

### Что такое DevOps?Table of Contents:

**DevOps** — это культура и набор практик, направленных на улучшение взаимодействия между командами Development (разработка) и Operations (эксплуатация).

Главная идея DevOps заключается в том, чтобы разработка, тестирование и развёртывание программного обеспечения происходили быстрее, надёжнее и с меньшим количеством ручной работы.

DevOps — это не отдельный инструмент или язык программирования. Это подход к организации процессов разработки и эксплуатации.

**Основные проблемы, которые решает DevOps:**

- Отсутствие взаимодействия между разработчиками и специалистами по эксплуатации.
- Большое количество ручных операций.
- Долгое обнаружение ошибок.
- Сложности при развёртывании приложения.
- Отсутствие общей ответственности за результат.

### Основные принципы DevOps

- **Value Stream** — оптимизация всего процесса доставки ценности пользователю, от идеи до готового продукта.
- **Feedback** — получение обратной связи на каждом этапе разработки, чтобы быстрее обнаруживать проблемы.
- **Errors** — работа с ошибками, их анализ и использование полученного опыта для улучшения процессов.

### SDLC (Software Development Life Cycle)

SDLC — жизненный цикл разработки программного обеспечения. Он описывает основные этапы, через которые проходит продукт от возникновения идеи до его эксплуатации.

| Этап | Описание |
|---|---|
| Idea | Формирование идеи и определение проблемы |
| Analytics | Анализ требований и возможностей реализации |
| Backlog | Формирование списка задач |
| Development | Написание программного кода |
| Testing | Проверка работоспособности приложения |
| Deployment | Развёртывание приложения в целевой среде |
| Feedback | Получение обратной связи и улучшение продукта |

Эти этапы могут повторяться. После получения обратной связи команда может изменить требования, добавить новые функции или исправить ошибки.

### Роль DevOps в SDLC

DevOps помогает автоматизировать и объединить процессы разработки, тестирования и развёртывания.

Например, после изменения исходного кода система может автоматически запустить сборку приложения, выполнить тесты и подготовить его к развёртыванию.

Таким образом, уменьшается количество ручных операций, а ошибки обнаруживаются раньше.



## 2. Git и GitLab Fundamentals

Для понимания GitLab CI/CD необходимо различать Git и GitLab.

**Git** — распределённая система контроля версий. Она позволяет отслеживать изменения исходного кода, создавать ветки и объединять изменения.

**GitLab** — платформа для работы с Git-репозиториями, совместной разработки и автоматизации процессов CI/CD.

### Основные понятия Git

| Понятие | Описание |
|---|---|
| Repository | Хранилище проекта и истории изменений |
| Working Directory | Рабочая директория, в которой изменяются файлы |
| Staging Area | Область подготовки изменений перед commit |
| Commit | Сохранённый набор изменений |
| Branch | Отдельная ветка разработки |
| Merge | Объединение изменений из разных веток |
| Remote | Удалённый Git-репозиторий |
| Push | Отправка локальных изменений в удалённый репозиторий |
| Pull | Получение изменений из удалённого репозитория с их интеграцией |
| Merge Request | Запрос на объединение изменений в другую ветку |

### Основной рабочий процесс

```bash
git add .
git commit -m "Add new feature"
git push
```

1. `git add` добавляет изменения в Staging Area.
2. `git commit` сохраняет изменения в локальной истории Git.
3. `git push` отправляет commits в удалённый репозиторий.

После push GitLab может запустить CI/CD pipeline, если в проекте настроен соответствующий `.gitlab-ci.yml` и условия запуска совпадают.

Важно: сам по себе `git push` не гарантирует запуск pipeline. Это зависит от конфигурации проекта и типа события.

### Merge Request

Merge Request (MR) — механизм GitLab, позволяющий предложить объединение изменений из одной ветки в другую.

Например, разработчик создаёт ветку `feature/login`, реализует авторизацию и отправляет её в GitLab.

После этого он создаёт Merge Request в `main`. Команда может проверить изменения, обсудить их и выполнить автоматические проверки до объединения веток.

Merge Request часто используется как триггер для запуска тестов и других проверок CI/CD.

## 3. GitLab CI/CD Architecture

GitLab CI/CD состоит из нескольких компонентов, которые взаимодействуют для автоматизации выполнения задач.

### Основные компоненты

**GitLab** — управляет репозиторием, pipeline, jobs и их состоянием.

**`.gitlab-ci.yml`** — конфигурационный файл, в котором описывается структура pipeline, стадии, jobs, команды и условия выполнения.

**Pipeline** — последовательность автоматизированных процессов, запускаемых определённым событием.

**Stage** — логический этап pipeline, объединяющий связанные jobs.

**Job** — отдельная задача, содержащая команды, которые должен выполнить Runner.

**Runner** — исполнитель, который получает jobs от GitLab и выполняет их.

### Как взаимодействуют компоненты

1. Разработчик отправляет изменения в GitLab.
2. GitLab проверяет конфигурацию `.gitlab-ci.yml`.
3. Создаётся pipeline.
4. Jobs распределяются по стадиям.
5. GitLab помещает jobs в очередь выполнения.
6. Подходящий Runner получает job.
7. Runner выполняет команды из `script`.
8. Runner отправляет результаты и логи обратно в GitLab.
9. GitLab обновляет состояние pipeline.

### Job Queue и Pending

Когда job создана, но ещё не начала выполняться, она может находиться в состоянии `pending`.

Это означает, что GitLab ожидает подходящего свободного Runner.

Причины, по которым job может долго оставаться в Pending:

- Нет доступного Runner.
- Runner находится offline.
- Теги job не совпадают с тегами Runner.
- Runner не включён для проекта.
- Все доступные Runner заняты.

## 4. GitLab Runner

GitLab Runner — приложение, которое получает jobs от GitLab и выполняет команды, указанные в конфигурации pipeline.

GitLab управляет pipeline, а Runner непосредственно исполняет jobs.

### Установка и регистрация Runner

Важно различать два процесса:

- **Install** — установка приложения GitLab Runner на машину.
- **Register** — регистрация Runner в GitLab и его привязка к соответствующему уровню или проекту.

Установленный, но не зарегистрированный Runner ещё не сможет получать jobs конкретного проекта.

При регистрации Runner настраиваются его параметры, включая executor и теги.

### Executors

Executor определяет, в каком окружении Runner будет выполнять jobs.

| Executor | Описание | Особенности |
|---|---|---|
| Shell | Выполняет команды непосредственно в shell машины Runner | Необходимые инструменты должны быть установлены на хосте |
| Docker | Запускает jobs в Docker-контейнерах | Окружение определяется Docker image |
| Kubernetes | Запускает jobs в Kubernetes Pods | Требуется Kubernetes-инфраструктура |

**Shell executor**

Команды выполняются непосредственно на машине, где установлен Runner.

Например, если job использует `go build`, Go должен быть установлен на этой машине.

Преимущество — простота настройки. Недостаток — ограниченная изоляция между jobs.

**Docker executor**

Каждая job выполняется в контейнере на основе указанного Docker image.

Например:

```yaml
image: golang:1.25

build_job:
  script:
    - go build ./...
```

В этом случае job получает окружение с Go из соответствующего Docker image.

Docker executor обеспечивает лучшую изоляцию окружения, но сам по себе не гарантирует полную безопасность.

**Kubernetes executor**

Каждая job выполняется в отдельном Kubernetes Pod. Такой подход полезен для масштабируемой CI/CD-инфраструктуры.

### Runner Tags

Tags позволяют направлять jobs на подходящие Runner.

Например:

```yaml
build_job:
  tags:
    - docker
    - linux
  script:
    - go build ./...
```

Если job содержит несколько тегов, Runner должен иметь все эти теги, чтобы получить job.

Также существует настройка `Run untagged jobs`, определяющая, может ли Runner выполнять jobs без тегов.

### Уровни Runner

Runner может быть зарегистрирован на разных уровнях:

- **Instance Runner** — доступен проектам в рамках GitLab-инстанса, если это разрешено настройками.
- **Group Runner** — доступен проектам определённой группы.
- **Project Runner** — привязан к конкретному проекту.

Эти уровни определяют область доступности Runner, а не способ выполнения jobs.

### Безопасность Runner

Runner может выполнять команды с правами пользователя, от имени которого работает его процесс.

Поэтому важно:

- Использовать принцип наименьших привилегий.
- Ограничивать доступ к защищённым Runner.
- Не хранить секреты непосредственно в YAML.
- Не запускать непроверенный код с production-доступом.
- Осторожно использовать Docker privileged mode.
- Ограничивать доступ к deployment-инфраструктуре.

## 5. Конфигурация `.gitlab-ci.yml` и YAML

`.gitlab-ci.yml` — основной конфигурационный файл GitLab CI/CD.

Обычно он находится в корне Git-репозитория.

В нём определяются стадии pipeline, jobs, команды, переменные, artifacts, cache и условия выполнения.

### Основы YAML

YAML — текстовый формат сериализации данных, который использует отступы для определения структуры.

Основные правила:

- Для отступов используются пробелы, а не табуляция.
- Вложенность определяется отступами.
- Комментарии начинаются с `#`.
- Пары ключ-значение записываются через двоеточие.
- Списки обозначаются дефисом.

Пример:

```yaml
stages:
  - build
  - test
  - deploy
```

### Stages и Jobs

`stages` определяет список стадий pipeline и их порядок.

```yaml
stages:
  - build
  - test
  - deploy
```

Job определяет конкретную задачу.

```yaml
build_job:
  stage: build
  script:
    - echo "Building application"
    - go build ./...
```

В этом примере:

- `build_job` — название job.
- `stage` — стадия, к которой относится job.
- `script` — команды, которые должен выполнить Runner.

### Основные параметры конфигурации

| Параметр | Назначение |
|---|---|
| `stages` | Определяет порядок стадий |
| `stage` | Назначает job определённой стадии |
| `script` | Содержит выполняемые команды |
| `before_script` | Команды, выполняемые перед основным script |
| `after_script` | Команды, выполняемые после script |
| `image` | Docker image для выполнения job при использовании подходящего executor |
| `variables` | Определяет переменные окружения |
| `tags` | Ограничивает выбор Runner |
| `timeout` | Ограничивает продолжительность выполнения job |
| `when` | Определяет условие выполнения job относительно результата предыдущих jobs |
| `allow_failure` | Позволяет pipeline продолжиться после допустимой ошибки job |

`before_script` используется для подготовки окружения перед основными командами.

`after_script` используется для дополнительных действий после выполнения основного script. Он выполняется в отдельном shell-контексте, поэтому не следует рассчитывать на сохранение всех изменений shell-состояния из `script`.

### Variables

Переменные позволяют хранить значения, которые используются в разных jobs.

Пример:

```yaml
variables:
  APP_NAME: "log-analyzer"

build_job:
  script:
    - echo "Building $APP_NAME"
```

GitLab также предоставляет predefined variables — встроенные переменные с информацией о текущем pipeline, проекте, ветке и других параметрах.

Примеры:

| Переменная | Значение |
|---|---|
| `CI_COMMIT_BRANCH` | Имя текущей ветки в branch pipeline |
| `CI_COMMIT_REF_SLUG` | Безопасное для использования имя текущей Git-ссылки |
| `CI_PIPELINE_SOURCE` | Источник запуска pipeline |
| `CI_PROJECT_DIR` | Путь к рабочей директории проекта |

Секретные значения, например пароли и SSH private keys, следует хранить в GitLab CI/CD Variables, а не непосредственно в `.gitlab-ci.yml`.

### CI Lint

GitLab CI Lint позволяет проверить синтаксис и корректность конфигурации `.gitlab-ci.yml`.

Это полезно, поскольку даже небольшая ошибка в отступах, названиях параметров или структуре YAML может привести к невозможности создания pipeline.

## 6. Stages, Jobs и выполнение Pipeline

Pipeline состоит из стадий, каждая из которых объединяет определённые jobs.

Например:

```yaml
stages:
  - build
  - test
  - deploy
```

### Последовательное выполнение стадий

По умолчанию стадии выполняются последовательно.

Следующая стадия обычно начинается после успешного завершения всех обязательных jobs предыдущей стадии.

Например:

1. Build.
2. Test.
3. Deploy.

Если обязательная job в стадии Test завершается ошибкой, следующая стадия Deploy обычно пропускается.

### Параллельное выполнение jobs

Jobs, находящиеся в одной стадии, могут выполняться параллельно, если для них доступны подходящие Runner и свободные ресурсы.

Пример:

```yaml
stages:
  - build
  - test
  - deploy

build_app:
  stage: build
  script:
    - echo "Building application"

build_docs:
  stage: build
  script:
    - echo "Building documentation"

unit_tests:
  stage: test
  script:
    - echo "Running unit tests"

integration_tests:
  stage: test
  script:
    - echo "Running integration tests"

deploy_app:
  stage: deploy
  script:
    - echo "Deploying application"
```

`build_app` и `build_docs` могут выполняться параллельно.

После завершения стадии Build могут запуститься `unit_tests` и `integration_tests`, также параллельно.

### Состояния Jobs

| Состояние | Значение |
|---|---|
| Created | Job создана |
| Pending | Ожидает Runner |
| Running | Выполняется |
| Success | Завершилась успешно |
| Failed | Завершилась с ошибкой |
| Canceled | Отменена |
| Skipped | Пропущена |

### Обработка ошибок

Если одна job завершается ошибкой, другие jobs той же стадии не обязательно останавливаются немедленно.

Они могут завершиться самостоятельно.

Однако ошибка обязательной job обычно блокирует переход к следующей стадии.

Параметр `allow_failure: true` позволяет считать ошибку конкретной job допустимой для продолжения pipeline.

Пример:

```yaml
optional_check:
  stage: test
  script:
    - echo "Optional check"
    - exit 1
  allow_failure: true
```

В этом случае job может завершиться с ошибкой, но pipeline сможет продолжиться.

Для анализа выполнения pipeline используются Pipeline Graph и Job Logs. Они позволяют определить, какие jobs запустились, какие были пропущены и на каком этапе возникла ошибка.

## 7. Artifacts и Cache

Artifacts и Cache позволяют сохранять файлы, но предназначены для разных задач.

### Artifacts

**Artifact** — результат выполнения job, который GitLab сохраняет для дальнейшего использования или скачивания.

Примеры:

- Собранное приложение.
- Исполняемый файл.
- Отчёт о тестировании.
- Архив с результатами сборки.
- HTML-отчёт.

Пример:

```yaml
build_job:
  stage: build
  script:
    - mkdir -p dist
    - echo "Build complete" > dist/build_output.txt
  artifacts:
    paths:
      - dist/
    expire_in: 1 week
```

Основные параметры:

| Параметр | Назначение |
|---|---|
| `artifacts` | Определяет настройки сохранения результатов |
| `paths` | Указывает файлы и директории для сохранения |
| `expire_in` | Определяет срок хранения artifact |
| `when` | Определяет, при каких результатах job сохранять artifacts |

Пути в `artifacts:paths` указываются относительно рабочей директории проекта.

По умолчанию GitLab загружает artifacts из предыдущих стадий в последующие jobs. Это поведение можно контролировать с помощью `dependencies` и `needs`.

Важно: по умолчанию artifacts сохраняются при успешном выполнении job. Для сохранения при других результатах можно использовать соответствующий параметр `when`, например `always`.

### Cache

**Cache** — механизм повторного использования файлов для ускорения последующих запусков jobs и pipeline.

Чаще всего кэшируются зависимости проекта.

Например:

- Go modules.
- npm dependencies.
- Python packages.
- Другие повторно используемые файлы.

Пример:

```yaml
variables:
  GOMODCACHE: "$CI_PROJECT_DIR/.go/pkg/mod"

cache:
  key: "$CI_COMMIT_REF_SLUG"
  paths:
    - .go/pkg/mod/
```

Основные параметры:

| Параметр | Назначение |
|---|---|
| `cache` | Определяет настройки кэширования |
| `key` | Определяет идентификатор cache |
| `paths` | Указывает директории для кэширования |
| `policy` | Определяет, как job использует cache: скачивает, загружает или делает и то и другое |

Cache может отсутствовать или быть недоступен. Поэтому он не должен быть обязательным условием корректной работы приложения.

### Artifacts vs Cache

| Критерий | Artifacts | Cache |
|---|---|---|
| Основная цель | Сохранение результатов работы | Ускорение выполнения |
| Типичные файлы | Собранное приложение, отчёты | Зависимости и повторно используемые файлы |
| Использование | Передача результатов между jobs | Повторное использование файлов |
| Надёжность наличия | Зависит от успешного сохранения и срока хранения | Не гарантируется |

Пример для Go-проекта:

- Исполняемый файл `log-analyzer` после сборки — Artifact.
- Загруженные Go modules — Cache.

## 8. Зависимости Jobs: `needs` и `dependencies`

В GitLab CI/CD jobs могут зависеть друг от друга.

Для управления зависимостями используются `needs` и `dependencies`, однако их назначение различается.

### `needs`

`needs` определяет зависимости между jobs и позволяет организовать выполнение pipeline в виде DAG (Directed Acyclic Graph).

DAG — ориентированный ациклический граф, в котором jobs могут запускаться сразу после завершения необходимых им зависимостей, не дожидаясь завершения всей предыдущей стадии.

Пример:

```yaml
stages:
  - build
  - test
  - deploy

build_app:
  stage: build
  script:
    - echo "Building app"

test_app:
  stage: test
  needs:
    - build_app
  script:
    - echo "Testing app"

build_docs:
  stage: build
  script:
    - echo "Building docs"

deploy_app:
  stage: deploy
  needs:
    - test_app
  script:
    - echo "Deploying app"
```

В этом примере `test_app` зависит от `build_app`, а `deploy_app` зависит от `test_app`.

`build_docs` не является зависимостью `test_app`, поэтому его выполнение не обязательно должно задерживать `test_app`.

Для управления передачей artifacts через `needs` используется параметр `artifacts`.

```yaml
test_app:
  stage: test
  needs:
    - job: build_app
      artifacts: true
  script:
    - ./log-analyzer
```

### `dependencies`

`dependencies` определяет, из каких jobs предыдущих стадий текущая job должна загружать artifacts.

Пример:

```yaml
build_app:
  stage: build
  script:
    - echo "Build" > output.txt
  artifacts:
    paths:
      - output.txt

build_docs:
  stage: build
  script:
    - echo "Docs" > docs.txt
  artifacts:
    paths:
      - docs.txt

test_app:
  stage: test
  dependencies:
    - build_app
  script:
    - cat output.txt
```

В этом случае `test_app` загружает artifacts только от `build_app`.

### Разница между `needs` и `dependencies`

| Критерий | needs | dependencies |
|---|---|---|
| Основная задача | Управление зависимостями и порядком выполнения | Управление загрузкой artifacts |
| Может ускорить pipeline | Да | Нет, само по себе |
| DAG execution | Да | Нет |
| Контроль artifacts | Да, через `artifacts` | Да, через список jobs |

Важно: `needs` и `dependencies` решают разные задачи. Не следует использовать их вместе в одной job. При использовании `needs` список необходимых jobs также определяет, откуда можно получать artifacts, если их загрузка разрешена.

## 9. Условия выполнения Jobs: `rules`, `only` и `except`

Не все jobs должны выполняться при каждом запуске pipeline.

Например, Deploy может быть необходим только для ветки `main`, а тесты могут запускаться при создании Merge Request.

Для управления условиями выполнения используются `rules`, а в старых конфигурациях — `only` и `except`.

### `only`

`only` определяет, при каких условиях job должна запускаться.

```yaml
deploy_job:
  stage: deploy
  script:
    - echo "Deploying..."
  only:
    - main
```

Job запускается только при соответствующих условиях, указанных в конфигурации.

### `except`

`except` определяет условия, при которых job не должна запускаться.

```yaml
deploy_job:
  stage: deploy
  script:
    - echo "Deploying..."
  except:
    - develop
```

В этом случае job не запускается для ветки `develop`.

`only` и `except` считаются устаревшим способом настройки условий. Для новых конфигураций рекомендуется использовать `rules`.

### `rules`

`rules` позволяет задавать условия запуска jobs.

Пример:

```yaml
deploy_job:
  stage: deploy
  script:
    - echo "Deploying..."
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: on_success
    - when: never
```

GitLab проверяет правила сверху вниз и применяет первое совпавшее правило.

Если ни одно правило не совпало, job не добавляется в pipeline.

### Основные значения `when`

| Значение | Назначение |
|---|---|
| `on_success` | Выполнение при успешном завершении необходимых предыдущих jobs |
| `on_failure` | Выполнение при ошибке предыдущих jobs |
| `always` | Выполнение независимо от результата предыдущих jobs |
| `manual` | Ручной запуск пользователем |
| `never` | Job не запускается |

### `CI_PIPELINE_SOURCE`

Переменная `CI_PIPELINE_SOURCE` определяет источник запуска pipeline.

| Значение | Источник |
|---|---|
| `push` | Push в Git-репозиторий |
| `merge_request_event` | Событие Merge Request |
| `schedule` | Запуск по расписанию |
| `web` | Ручной запуск через GitLab UI |
| `api` | Запуск через API |

Пример запуска тестов для Merge Request:

```yaml
test_job:
  stage: test
  script:
    - go test ./...
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
```

### `rules:changes`

`rules:changes` позволяет запускать job только при изменении определённых файлов или директорий.

Пример:

```yaml
frontend_tests:
  stage: test
  script:
    - echo "Testing frontend"
  rules:
    - changes:
        - frontend/**/*
```

В этом случае job будет добавлена в pipeline, если изменения затрагивают файлы внутри `frontend`.

Пути указываются относительно корня Git-репозитория.

## 10. Monorepo и Downstream Pipelines

### Monorepo

**Monorepo** — подход, при котором несколько проектов или модулей хранятся в одном Git-репозитории.

Пример структуры:

```text
monorepo/
├── .gitlab-ci.yml
└── MysticArchive/
    ├── frontend/
    ├── backend/
    ├── auth/
    ├── database/
    └── notifications/
```

Каждый модуль может иметь собственную конфигурацию CI/CD.

Основная проблема monorepo заключается в том, что изменение одного модуля не всегда требует запуска pipeline для всех остальных модулей.

Для решения этой задачи используется `rules:changes`.

Например:

```yaml
frontend_tests:
  stage: test
  script:
    - echo "Testing frontend"
  rules:
    - changes:
        - MysticArchive/frontend/**/*
```

Если изменились только файлы frontend, соответствующая job запускается, а ненужные проверки других модулей могут быть пропущены.

### Parent и Child Pipelines

Для разделения CI/CD-конфигурации можно использовать Parent и Child Pipelines.

**Parent Pipeline** — родительский pipeline, который запускает дочерние pipeline.

**Child Pipeline** — дочерний pipeline, который выполняет собственные jobs и stages.

Например, корневой pipeline может запускать отдельные дочерние pipeline для frontend, backend и auth.

### `trigger` и `include: local`

`trigger` используется для запуска downstream pipeline.

`include: local` указывает путь к YAML-файлу, конфигурация которого будет использоваться дочерним pipeline.

Пример:

```yaml
stages:
  - modules

frontend_pipeline:
  stage: modules
  trigger:
    include:
      - local: 'MysticArchive/frontend/.gitlab-ci.yml'
    strategy: depend
  rules:
    - changes:
        - MysticArchive/frontend/**/*
```

В этом примере:

- `trigger` запускает Child Pipeline.
- `include: local` указывает его конфигурационный файл.
- `strategy: depend` заставляет родительский pipeline ждать завершения дочернего и учитывать его результат.
- `rules:changes` ограничивает запуск изменениями соответствующего модуля.

### `strategy: depend`

При использовании `strategy: depend` trigger job ожидает завершения дочернего pipeline.

Если дочерний pipeline завершился успешно, trigger job завершается успешно.

Если дочерний pipeline завершился с ошибкой, trigger job также получает ошибочный статус.

В актуальных конфигурациях GitLab также рекомендуется рассматривать `strategy: mirror`, который зеркально отражает статус downstream pipeline. В учебном примере используется `depend`.

### Преимущества Child Pipelines

- Разделение конфигурации по модулям.
- Более удобное сопровождение большого monorepo.
- Возможность запускать только необходимые pipeline.
- Независимая логика сборки и тестирования модулей.
- Более понятная структура CI/CD.

## 11. Deployment, SSH и типы Runner

### Deployment

**Deployment** — процесс развёртывания приложения в целевом окружении.

Это может быть удалённый Linux-сервер, облачная инфраструктура, Kubernetes-кластер или другая среда выполнения.

В CI/CD deployment обычно выполняется после успешной сборки и тестирования приложения.

### SSH (Secure Shell)

SSH — протокол для безопасного подключения к удалённым машинам и выполнения команд.

Пример подключения:

```bash
ssh username@192.168.1.100
```

После подключения можно выполнять команды на удалённом сервере.

### SSH Keys

Для аутентификации часто используются пары SSH-ключей:

- **Private Key** — секретный ключ, который хранится у клиента.
- **Public Key** — открытый ключ, который добавляется на сервер.

Public key обычно размещается в файле:

```text
~/.ssh/authorized_keys
```

Private key нельзя публиковать или хранить в открытом виде в Git-репозитории.

Для CI/CD private key можно хранить в GitLab CI/CD Variables.

### `known_hosts`

`known_hosts` — файл, содержащий проверенные SSH host keys удалённых серверов.

Он позволяет SSH-клиенту проверять подлинность сервера при подключении.

Отключать проверку host key без необходимости небезопасно, поскольку это увеличивает риск атак типа Man-in-the-Middle.

### SSH Deployment в GitLab CI/CD

Для автоматического подключения к серверу через GitLab CI/CD обычно используются следующие переменные:

| Variable | Назначение |
|---|---|
| `SSH_PRIVATE_KEY` | Private key для подключения |
| `SSH_KNOWN_HOSTS` | Проверенный host key сервера |
| `DEPLOY_USER` | Имя пользователя на сервере |
| `DEPLOY_HOST` | Адрес удалённого сервера |

Пример:

```yaml
deploy_job:
  stage: deploy
  before_script:
    - chmod 400 "$SSH_PRIVATE_KEY"
    - mkdir -p ~/.ssh
    - cp "$SSH_KNOWN_HOSTS" ~/.ssh/known_hosts
  script:
    - >
      scp -i "$SSH_PRIVATE_KEY"
      log-analyzer
      "$DEPLOY_USER@$DEPLOY_HOST:/home/$DEPLOY_USER/log-analyzer"
    - >
      ssh -i "$SSH_PRIVATE_KEY"
      "$DEPLOY_USER@$DEPLOY_HOST"
      "chmod +x ~/log-analyzer && ~/log-analyzer"
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```

В примере используются две команды:

- `scp` — копирование файлов между локальной и удалённой машинами.
- `ssh` — подключение к удалённой машине и выполнение команд.

Это базовая учебная схема. Для production обычно дополнительно настраивают управление процессом через systemd или Docker, health checks, логирование и механизм rollback.

### Shared Runner и Own Runner

**Shared Runner** — Runner, предоставляемый для совместного использования несколькими проектами в рамках соответствующей конфигурации GitLab.

**Own Runner (Self-managed Runner)** — Runner, установленный и обслуживаемый владельцем собственной инфраструктуры.

| Критерий | Shared Runner | Own Runner |
|---|---|---|
| Установка | Обычно не требуется | Самостоятельная |
| Обслуживание | Управляется провайдером | Самостоятельное |
| Контроль окружения | Ограниченный | Более высокий |
| Настройка executor | Зависит от провайдера | Можно выбирать |
| Инфраструктура | Общая | Собственная |
| Ответственность | В основном провайдер | Владелец Runner |

**Shared Runner** удобен для небольших проектов и быстрого начала работы с CI/CD.

**Own Runner** подходит для проектов, которым требуется собственное окружение, дополнительные ресурсы или доступ к внутренней инфраструктуре.

Важно: Own Runner не обязательно использует Docker. Он может работать с Shell, Docker или другим поддерживаемым executor.

### Общая последовательность настройки Own Runner

1. Install — установка GitLab Runner.
2. Register — регистрация Runner в GitLab.
3. Configure — настройка executor и других параметров.
4. Run — запуск Runner.
5. Execute jobs — получение и выполнение jobs из pipeline.

### Основные выводы

GitLab CI/CD объединяет процессы сборки, тестирования и развёртывания приложения в автоматизированную систему.

Для эффективной работы с GitLab CI/CD необходимо понимать:

- как устроены Git и GitLab;
- из чего состоит pipeline;
- какую роль выполняет Runner;
- как настраиваются stages и jobs;
- как управлять зависимостями и передачей файлов;
- как задавать условия выполнения;
- как организовать CI/CD для monorepo;
- как безопасно развёртывать приложения на удалённых серверах.

Главная цель CI/CD — сделать процесс доставки программного обеспечения автоматизированным, повторяемым, контролируемым и надёжным.
